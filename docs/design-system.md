# Telemetrix 디자인 시스템

이 문서는 취향이 아니라 **측정과 규칙**을 적는다. 화면을 새로 만들거나 고칠 때
여기 있는 값만 쓰고, 여기 없는 값을 쓰고 싶으면 먼저 이 문서를 고친다.

구현: [`lib/core/theme/design_tokens.dart`](../lib/core/theme/design_tokens.dart),
[`lib/core/theme/app_theme.dart`](../lib/core/theme/app_theme.dart)

---

## 왜 만들었나 — 값이 흩어져 있었다

색은 이미 `AppSemanticColors`(ThemeExtension)로 잘 토큰화돼 있었다. 나머지는 아니었다.
코드 전체를 세어보니:

| 항목 | 서로 다른 값 | 실제로 쓰이던 값 |
| --- | ---: | --- |
| padding / margin | **19종** | 3, 5, 7, 9, 11, 12, 14, 16, 20, 24, 28, 32 … |
| borderRadius | **10종** | 7, 8, 10, 12, 14, 16, 18, 20, 28, 100 |
| 간격 (SizedBox) | **18종** | 2, 3, 4, 6, 8, 10, 12, 14, 16, 18, 20, 24 … |
| fontSize | **15종** | **9.5, 10.5, 11.5, 12.5**, 11, 12, 13, 14, 15, 16, 17 … |

반 포인트 글자 크기(9.5·10.5·11.5·12.5)와 3·5·7·9·11 패딩은 스케일 없이 **그때그때
눈으로 맞췄다**는 뜻이다. 값 하나하나는 그럴듯해 보여도 모아놓으면 리듬이 없어서,
화면을 넘길 때마다 미묘하게 다른 앱처럼 느껴진다. 이게 "만들다 만 느낌"의 정체다.

적용 후 스케일을 벗어난 값은 **164곳 → 14곳**으로 줄었다(남은 건 대부분 아이콘 크기 등 의미 있는 치수).

## 원칙

1. **정보 위계를 시각 효과보다 앞에 둔다.** 무엇이 중요한지는 크기·색·배치로 말한다.
   그림자와 그라데이션으로 말하지 않는다.
2. **보조 정보는 보조로 보이게 한다.** DTC 코드처럼 참고용인 것을 진한 배경으로 칠하면
   화면에서 가장 무거운 요소가 되어 위계가 뒤집힌다. 테두리 알약으로 낮춘다.
3. **모서리는 또렷하게.** 과하게 둥근 모서리와 그라데이션 버튼의 조합은 흔한
   "생성형 앱" 인상을 만든다. 계측 도구에는 정확해 보이는 모서리가 맞는다.
4. **글자 배율을 무시하지 않는다.** 사용자가 1.5배로 키우면 커져야 한다. 대신
   잘리지 않게 [`FittedBox`]나 `Flexible` + 말줄임으로 받아낸다.
5. **숫자는 폭이 흔들리지 않게.** 계측값은 tabular figures로 렌더한다
   (`AppTheme.gaugeNumberStyle`). 값이 바뀔 때 레이아웃이 덜컹거리면 안 된다.

## 간격 — 4pt 그리드

Material과 Apple HIG가 공통으로 쓰는 기준이다. 4는 아이콘·조밀한 수치 표시에,
8 이상은 레이아웃에 쓴다.

| 토큰 | 값 | 쓰는 곳 |
| --- | ---: | --- |
| `Spacing.xxs` | 4 | 아이콘과 라벨 사이처럼 붙어 있어야 하는 것 |
| `Spacing.xs` | 8 | 같은 덩어리 안의 요소 사이 |
| `Spacing.sm` | 12 | 카드 내부의 행 사이 |
| `Spacing.md` | 16 | 카드 안쪽 여백, 화면 좌우 여백의 기본값 |
| `Spacing.lg` | 24 | 서로 다른 섹션 사이 |
| `Spacing.xl` | 32 | 화면 상단/하단의 큰 여백 |
| `Spacing.xxl` | 48 | 랜딩처럼 여백 자체가 메시지인 곳에서만 |

`context.screenPadding`은 360px 미만에서 `md` 대신 `sm`을 돌려준다 — 좁은 화면에서는
여백보다 내용 폭이 중요하다.

## 모서리 — 8 / 12 / 20 / 알약

| 토큰 | 값 | 쓰는 곳 |
| --- | ---: | --- |
| `Radii.sm` | 8 | 버튼, 입력창, 작은 컨테이너 |
| `Radii.md` | 12 | 카드 — 이 앱의 기본 표면 단위 |
| `Radii.lg` | 20 | 바텀시트, 모달처럼 화면을 덮는 표면 |
| `Radii.pill` | 999 | 상태 배지, 칩 |

반경이 여러 개면 "무엇이 더 중요한 요소인가"를 반경으로 말할 수 없게 된다.
표면이 클수록 반경도 커지는 규칙 하나만 지킨다.

## 글자 — 6단

| 토큰 | 값 | 쓰는 곳 |
| --- | ---: | --- |
| `FontSizes.display` | 32 | 대시보드의 대표 수치 하나, 태블릿 이상의 제목 |
| `FontSizes.displayCompact` | 24 | 태블릿 미만 폭의 제목 (`context.displayFontSize`) |
| `FontSizes.title` | 20 | 화면 제목, 보조 계측값 |
| `FontSizes.subtitle` | 16 | 카드 제목, 버튼, 앱바 |
| `FontSizes.body` | 14 | 본문 기본값 |
| `FontSizes.caption` | 12 | 보조 설명, 라벨 |
| `FontSizes.badge` | 11 | 배지 안의 글자. **이보다 작게는 쓰지 않는다** |

계측 수치는 별도 단을 만들지 않고 위 단을 쓰되 서체만 tabular figures로 바꾼다.

## 터치 타겟

`TouchTarget.min = 48`. 아이콘이 작아 보여야 하는 곳도 **눌리는 영역**은 이 값을 지킨다.
차량 카드의 `⋮` 메뉴가 그 예다 — 아이콘은 20이지만 `SizedBox(48, 48)`로 감싼다.

## 화면 너비

| 토큰 | 값 | 의미 |
| --- | ---: | --- |
| `Widths.compact` | 320 | **지원하는 최소 너비.** 이 아래는 대상이 아니다 |
| `Widths.regular` | 360 | 흔한 안드로이드 폰 |
| `Widths.tablet` | 600 | 이 위부터 태블릿 레이아웃 |
| `Widths.desktop` | 1024 | 데스크톱 브라우저 |

## 내용 폭 — 넓은 화면에서 한 줄이 얼마나 길어져도 되는가

화면마다 `maxWidth`를 따로 정해 쓰고 있었고, 세어보니 **420 / 480 / 600 / 700 / 800 /
900 / 1100 / 1200 — 8종**이었다. 간격·글자에서 고쳤던 것과 같은 "규칙 없음" 문제다.

기준은 폭 자체가 아니라 **한 줄에 무엇이 들어가는가**다.

| 토큰 | 값 | 쓰는 곳 | 왜 |
| --- | ---: | --- | --- |
| `ContentWidths.form` | 480 | 로그인, 차량 등록 | 폼은 넓다고 좋아지지 않는다. 입력란이 길어지면 라벨↔값 시선 이동만 늘어난다 |
| `ContentWidths.reading` | 640 | 설정, 진단 결과 | 권장 행 길이(45~75자)를 본문 크기에서 넘지 않는 폭 |
| `ContentWidths.feed` | 840 | 이상 이력 목록 | 카드 안에 배지·수치가 가로로 놓여 본문보다 여유가 필요하다 |
| `ContentWidths.grid` | 1200 | 대시보드, 차량 목록, 랜딩 | 열이 여러 개면 각 열이 알아서 제한된다 |

폭을 제한하지 않으면 1280px에서 차량 이름은 왼쪽 끝, 상태 배지는 오른쪽 끝이 되어
**눈이 화면을 가로질러야 한다.** `test/golden/snapshots/light_1280_unbounded.png`와
`light_1280_feed.png`를 나란히 보면 차이가 그대로 보인다.

### 폭 제한만으로는 부족한 경우가 있다

카드를 넓히면 **안이 비는** 요소가 있다. 계측 카드의 아크 게이지가 그랬다 —
크기가 104~144px로 고정돼 있어서, 카드가 커져도 게이지는 그대로고 카드의 3/4이
빈 채로 남았다(1280px 스냅샷에서 발견). 상한을 220으로 올려 카드와 함께 커지게 했다.
**하한(104)은 그대로 둔다** — 그 아래로 줄면 게이지 안 숫자가 `FittedBox`에 눌린다.

## 그라데이션 — 랜딩·로그인에만 쓴다

`primaryGradient`는 랜딩 히어로와 로그인의 주 CTA **두 곳**에만 쓴다.
그 두 화면은 제품을 소개하는 표면이고, 나머지는 계측 도구다. 원칙 3번(또렷한 모서리)이
말하는 "생성형 앱 인상"은 과한 라운딩과 그라데이션이 **화면 전체에 깔릴 때** 생긴다.
진입 화면에 한정하면 성격이 다르므로 그대로 둔다.

`accentGlow`(주 색상 번짐 그림자)는 **테마에만 있고 아무 데서도 쓰지 않았다.**
지웠다. 지우고 나니 `AppSemanticColors` 전체가 `const`가 됐다(유일한 non-const
필드였다).

## 컴포넌트 패턴

### 목록 카드는 가로로 경쟁시키지 않는다

가장 많이 반복된 실수다. 바깥 `Row`에 고정 폭 요소를 나란히 두고 그중 하나에만
`Expanded`를 주면, 나머지가 폭을 양보하지 않아 좁은 화면에서 잘린다.
실제로 **차량 카드는 320px에서 기본 글자 크기로도 99px가 넘쳐** 있었다.

```
[아이콘] 차량 이름                    ● 정상  [⋮]
         #KR-GA-1234  홍길동
         118 km/h · HIGH 12 · 5분 전 수신
```

- 세로로 쌓고, 마지막 줄은 `Wrap`으로 흘려보낸다 — 폭이 모자라면 줄바꿈된다.
- 상태는 **한 줄 알약**으로. 두 줄 배지는 폭을 두 배로 먹는다.
- 카드 전체가 눌리면 `chevron`은 넣지 않는다. 어포던스가 셋이 되고,
  그 화살표가 좁은 화면에서 폭을 가장 많이 가져간다.

### 고정 크기 안의 글자는 FittedBox로 받는다

아크 게이지처럼 정사각 고정 크기 안에 글자를 넣는 곳은, 글자 배율 1.5배에서
반드시 넘친다. 배율을 무시하면 접근성이 깨지므로 `FittedBox(fit: scaleDown)`으로
"공간이 있으면 커지고 모자라면 줄어들게" 한다.

### 제목에 수동 줄바꿈을 쓰지 않는다

제목 문자열 안에 줄바꿈 문자를 직접 넣어 줄을 잡으면 특정 폭을 가정하는 것이라, 그 폭이 아니면 고아 줄이 생긴다(360px에서 "차량 상태와 데이터 /
흐름을 / 한눈에 확인하기"가 됐다).

줄바꿈 위치를 손으로 잡는 대신 **글자 크기를 폭에 맞춘다**. `context.displayFontSize`가
태블릿 미만에서 32 → 24로 낮춰, 자동 줄바꿈이 균형 잡힌 두 줄을 만든다.

### 한 줄 라벨은 Expanded + 말줄임

`Row` 안의 텍스트는 거의 항상 `Expanded`/`Flexible` + `maxLines` + `ellipsis`가 필요하다.
없으면 글자 배율이 올라가는 순간 넘친다.

## 검증

디자인은 눈으로 확인해야 하지만, **회귀는 자동으로 잡는다.**

### 반응형 자동 검사

```bash
flutter test test/responsive_overflow_test.dart
```

구성 요소 × 너비 6종(320/360/400/768/**1024/1280**) × 글자 배율 3종(1.0/1.3/1.5) 조합을 전부 돌며
Flutter가 렌더 단계에서 보고하는 overflow를 테스트 실패로 만든다.
AGENTS.md 체크리스트의 두 항목을 코드로 옮긴 것이다.

**구성 요소는 실제로 쓰이는 형태로 넣어야 한다.** 계측 카드를 전체 폭으로만 검사했더니
Row 안 절반 폭에서 나는 overflow를 놓쳤다. 목록 카드는 목록에 놓이는 형태로,
나란히 쓰이는 카드는 나란히 둔 형태로 검사한다.

### 스냅샷 확인

```bash
flutter test test/golden --update-goldens --run-skipped
# test/golden/snapshots/*.png 를 열어서 본다
```

라이트/다크 × 320/360/**1280** × 글자 1.5배를 PNG로 뽑는다. **회귀 감지가 아니라
확인용**이라 기본 실행에서는 제외한다(`dart_test.yaml`) — 폰트 렌더링이 환경마다
미세하게 달라 픽셀 비교를 CI에 넣으면 계속 깨진다.

1280px는 두 장을 뽑는다 — 폭 제한 없는 것과 `ContentWidths.feed`를 적용한 것.
overflow 검사는 "잘리지 않는가"만 보고 **"한 줄이 너무 길어 읽기 나쁜가"는 못 잡는다.**
그건 나란히 놓고 눈으로 판단할 수밖에 없다.

테스트 환경에는 google_fonts가 폰트를 받아올 수 없어 한글이 두부(□)로 렌더되므로,
시스템 한글 폰트를 `FontLoader`로 물려서 읽을 수 있게 해뒀다.

> **오프라인에서 이 스위트는 "실패"로 표시된다.** 테마가 `GoogleFonts.manrope()`를
> 쓰는데 폰트를 못 구하면 예외가 나고, 그 예외가 `fake_async` 존 안에서 비동기로
> 올라와 `FlutterError.onError`로 가로챌 수 없다(시도했고 안 된다).
> **PNG는 정상적으로 나온다** — 위 `FontLoader`가 같은 이름으로 폰트를 물려두기
> 때문이다. 실패 표시는 이미지 품질과 무관하니 `snapshots/*.png`를 열어보면 된다.

## 아직 안 한 것

- **스케일을 벗어난 값이 14곳 남아 있다.** 대부분 아이콘 크기와 레이아웃 치수처럼
  의미가 있어 기계적으로 바꾸면 안 되는 것들이지만, 하나씩 확인하지는 않았다.
- **실기기 검증을 하지 않았다.** 위 결과는 전부 `flutter test`(위젯 테스트) 기준이다.
  실제 기기의 폰트 렌더링, 스크롤 감, 터치 반응은 확인하지 못했다.
- **`ContentWidths`를 실제 화면 전체로 렌더해 보지는 않았다.** 스냅샷은 구성 요소를
  모아놓은 갤러리 기준이다. 화면마다 앱바·탭·여백이 더 붙으므로 체감 폭은 다를 수 있다.
- **대시보드 그리드의 열 수 기준(`isDesktop`이면 4열)은 그대로 뒀다.** 내용 폭이
  1200으로 바뀌었으니 열당 폭도 달라졌는데, 4열이 적정한지는 재검토하지 않았다.
